Implementation plan · qcdsp

Custom DSP blocks for the Quad Cortex, written in Rust

Proposed — awaiting approval 2026-10-05 Judah Fuller repo: ~/Projects/QC

Goal: write a DSP block in Rust, run one command, and get a block that appears in the Quad Cortex UI and processes audio on its SHARC+ cores. The investigation decoded everything after the compiler: the block file format, per-core variants, metadata, encryption and install. This plan builds an open Rust toolchain for the remaining part — code generation — and a small DSP language on top.

01What the investigation established

Hardware2× ADSP-SC589. Each: 1 ARM Cortex-A5 + 2 SHARC+ cores. Blocks run on 4 SHARC+ cores.
LoaderZenUI (ARM) is the linker: it lays out a preset, relocates each block and writes it into SHARC memory.
Block fileEncrypted ModuleBlob: code, data, relocations, link ranges, entry. All 371 stock blobs round-trip byte-for-byte.
Per-core variantsDiff records patch absolute kernel addresses. 188 kernel calls mapped across all 4 cores, no conflicts.
MetadataModelRepo.xml (UI, parameters) and moduleReport.xml (heap, code size, CPU). Both decrypt and re-encrypt.
Runtime ABICCES C run-time model. Entry fills a context struct of callback slots. Audio-callback arguments still to read.
CompilerNo LLVM/GCC/Rust target. CCES is licensed. selache (Rust, GPL) disassembles the QC blobs.
Prior artTim's NAM A2-Lite block (Sep 2026), shipped prebuilt with an installer. Proves the path works.

Details: research/custom-dsp-blocks.md, research/sharc-toolchain-landscape.md.

Why a DSP language and not general Rust: SHARC+ has delay slots, hardware loops and VLIW-style multifunction instructions, and no LLVM support. A small language with float math, parameters, state and delay lines covers what blocks need and lets the compiler use those features directly.

What writing a block could look like

Illustrative only — the real API is designed in milestone 4.

use qcdsp::prelude::*;

/// A drive: gain into a soft clipper, then output level.
#[derive(Block)]
#[block(name = "Simple Drive", category = Category::GuitarOverdrive)]
struct Drive {
    #[param(range = 0.0..=10.0, default = 5.0)]
    gain: Param,
    #[param(range = 0.0..=10.0, default = 5.0)]
    level: Param,
}

impl Process for Drive {
    fn process(&self, dsp: &mut Dsp, input: Signal) -> Signal {
        let driven = input * dsp.db_to_gain(self.gain * 4.0);
        dsp.soft_clip(driven) * (self.level / 10.0)
    }
}

// cargo qcdsp build   → target/qcdsp/simple_drive.qcblock
// cargo qcdsp install --host qc

06Risks and safety

Device writes. Installing a block rewrites four NDSP files and reboots. Every install makes a local and on-device backup and moves files atomically. A full SD-card image from 2026-10-05 exists as a last resort.
Firmware updates. Keys, seed location and kernel addresses can move when CorOS changes. All tools pin the exact ZenUI build and refuse unknown builds instead of guessing.
Resource figures. Under-reported heap or CPU makes ZenUI place blocks that do not fit and corrupt neighbours (Tim's August failures). The linker computes sizes; M4 measures them.
Licences and IP. selache is GPL-3.0: use it as a separate tool, never link it into the library. Never publish NDSP keys, firmware, decrypted stock blobs or the per-core kernel map; the library reads them from the user's own device.
Process killer. ZenUI kills unknown processes within seconds. On-device helpers must be short-lived, or the killer is patched (Tim's patch exists).
